# Issue, epic and closeout templates

Copy a template, fill every placeholder in angle brackets, and delete nothing but the placeholder text. Each template names the issues it was read from.

## Child issue

Read from #485–#517 (current form). #484 also links the plan on its `Parent:` line; the epic's Specification already links it, so the children leave it out. #130–#148 carry the same five parts under older headings; the mapping is at the end of this file.

Title: `[<Id>] <work package in one line>`, where `<Id>` is the epic letter and the child's number in the plan's work-package table (`A1`, `B12`, `C6`).

```markdown
Parent: #<epic> (Epic <letter>). <Plan|Audit>: section <n>. (or: sections <n> and <m>.)

## Scope
<What changes, named by file, export or route. One paragraph, or a numbered list when the steps have an order. Name the decision ids (D3, D9) the scope follows.>

## Affected files
<Backticked repository paths; mark new files with (new) and generated files with (generated).>

## Blocked by
<"None." or the blocker ids with their numbers: "A1 (#487), D2 (#485)." Add "(may run beside D1)" style notes when the plan allows it.>

## Acceptance
- [ ] <An observable outcome a reviewer can check, with the command, route or assertion that shows it.>
- [ ] <...>

## Verification
<The npm scripts to run, each in backticks, ending with `git diff --check`.>
```

## Epic

Read from #479–#483.

Title: `[Epic <letter>] <outcome in one line>`.

```markdown
<One paragraph: what the epic delivers and the owner decision behind it, with the date.>

## Specification
[<Plan name>](https://github.com/lukaskourilcz/react-express-app/blob/main/docs/<plan>.md), sections <n> and the Epic <letter> table in section <m>; decisions <D-ids> in section <k>.

## <Order | Conventions | Rules that hold for every child issue>
<Order: the arrows from the plan's blocker table, for example "A1 → A2 → A3 and A4 → A5".>
<Conventions or rules: bullets that bind every child, each citing its source.>

## Child issues
- <Id> #<number> <title without the [Id] prefix>
- <...>

## Done when
- <An end state with the command or route that proves it.>
- <The npm scripts that must pass.>
```

An epic created before its children carries the child map as a placeholder list of ids and titles. Edit the epic with the numbers once the children exist (`gh issue edit <epic> --body-file <file>`).

## Design-audit finding

Read from #270–#306 (`design-review-2`). #240–#264 (`design-audit`) use the same sections with two different lines: `Audit references: <page> <number>` with no Files part in place of the Files line, and `Audit page: [<page file>](...) — findings <page> <number>.` in place of the Review page line.

Title: `Design audit <P-id>: <finding>` or `Design review 2 <R2-P-id>: <finding>`. Labels: the audit label plus one priority label (`P0`, `P1` or `P2`).

```markdown
## Finding

<What is wrong, in one or two sentences.>

Files: <files> · Review reference: <page> <number>

## Fix (from `<brief path>`)

<The fix as the brief states it.>

## Source

Review page: [<page file>](https://github.com/lukaskourilcz/react-express-app/blob/main/<path>), <reference>.
```

## Closeout comment on an issue

Read from the comments on #128, #129, #143 and #148. Post it when the work merges, or when you leave an issue open on purpose.

```markdown
<One sentence: what is on `main` and at which commit, and whether this issue closes or stays open and why.>

## Verified here, with real runs

| Command | Result |
|---|---|
| `npm run <script>` | <pass, with the count it printed> |
| `git diff --check` | clean |

## Not verified here, and why

- **<Check>.** <Why this session could not run it, and the NEEDED.md entry that tracks it.>

---
_Generated by [Claude Code](https://claude.ai/code)_
```

When an issue reopens because newer requirements superseded what shipped, add a table of the conflicts, as the first #128 comment did:

```markdown
| Superseded by | What is on `main` |
|---|---|
| #<n> <requirement> | <the shipped behaviour that conflicts> |
```

## Closeout record for a batch of issues

Use it when one brief produced many issues, and post it as a comment on the epic or tracking issue. The September design-audit closeouts used this shape.

```markdown
## <Batch name> closeout (<date>)

<What closed, how many change ids, their issue range and labels, and the merge PRs in order.>

### Changes

| ID | Issue | Commit | Deviation from the brief |
|---|---|---|---|
| <id> <name> | #<n> | `<sha>` | <None. or what differs and why> |

### Validation (<branch or commit>, <date>)

| Check | Result |
|---|---|
| `npm run <script>` | <result> |

<One paragraph naming what was not run and why.>
```

## Older headings (#130–#148)

| Current heading | Heading in #130–#148 |
|---|---|
| `Parent:` line | `Parent: #128` or `Parent: #129` (the FDE or DSA epic; #130–#133 add "(shared with #129)") and a `## Specification` link line |
| `## Scope` | `## Why / scope` |
| `## Affected files` | `## Affected files` |
| `## Blocked by` | `## Dependencies`, one `- Blocked by #<n>: <title>` line per blocker, or "None. Start here." |
| `## Acceptance` | `## Acceptance criteria` |
| `## Verification` | `## Verification` |

The older order differs too: Why / scope, Specification, Dependencies, Affected files, Acceptance criteria, Verification, then a `## Delivery constraints` paragraph that repeated the epic's rules (and, on every one of them, a later `## September 8 requirement update` section). The current form puts Affected files before Blocked by and moves shared rules into the epic body.
