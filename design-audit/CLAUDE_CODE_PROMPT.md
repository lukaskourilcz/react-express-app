# devShark pre-launch design audit — implementation brief for Claude Code

Read this file first, then the audit pages under `design-audit/`. Work section by section, in the order below. This is a cut-and-tighten pass: no new features, pages, gamification or content. The shark identity stays (footer ocean, fin schools, loader fin, fins as lives, waterline kickers, the green); only the arcade vocabulary and the watermark copies go.

## How to work

- For **every numbered change** below, open one GitHub issue (`gh issue create`) titled `Design audit <ID>: <short title>`, body = the finding text and the fix, labelled `design-audit` and `P0`/`P1`/`P2`. Reference the audit page (e.g. `design-audit/04 Rewards.dc.html`, finding 2).
- Work on a branch per priority band (`audit/p0`, `audit/p1`, `audit/p2`). Commit after each change, never batch more than one ID per commit; message `Design audit <ID>: <title> (closes #<issue>)`. Push after every 2–3 commits so nothing is lost.
- Copy changes go through `client/src/i18n/translations.ts` **and** `translations.cs.ts` (keep the Czech dictionary in sync even though CS is not shown). When a key is deleted, delete it from both files and grep for its use.
- Run before every push: `npm run typecheck:api`, `npm run test:client`, `npm run test:launch`, `npm run build`. Fix failures in the same commit.
- Do not change grading, XP, scoring, streak or entitlement logic. Do not touch `shared/tiers.ts` behaviour. Where a change hides content behind a feature switch, use the switch that already exists (`shop.data.enabled`, `LEARNING_PATH_*_ENABLED`, `BILLING_ENABLED`).
- If a finding conflicts with something you see in the live code that the audit did not read (`Coding.css`, `Rewards.css`, `LearningPathsCard.tsx`, `GithubGardenCard.tsx`, `SocialProfiles.tsx`, `PlanLine.tsx`, `ChallengeRunPlanner.tsx`), prefer the intent of the finding and note the deviation in the issue.
